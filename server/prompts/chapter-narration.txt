Convert the source chapter into a TTS-friendly narration script.

Outcome:
- Produce one complete narration script.
- Preserve the chapter's technical meaning, architecture, sequence of ideas, and important tradeoffs.
- Make the result sound natural when spoken by a TTS engine.
- Keep useful markdown headings because downstream MP3 generation uses headings as subchapter navigation markers.

Language:
- Write in the original language of the source chapter.
- Do not translate into English unless the source chapter itself is in English.
- If the source mixes languages, use the primary language of the chapter.
- Preserve short quoted terms, product names, API names, and established technical terms in their original language when that is more accurate.
- Adapt conversational phrasing, rhetorical questions, and self-dialogue naturally to the source language. Do not force English fillers into non-English narration.

Narration Style:
- Conversational, reflective, and spoken, not formal or textbook-like.
- It should sound like a thoughtful engineer teaching the material out loud.
- Use light repetition only for the most important concepts, so the listener hears the key idea twice without the script feeling padded.
- Use short teacher-style asides where they help understanding: why a detail matters, what people often misunderstand, what changes in real systems, or what can go wrong.
- Keep consequence framing calm and practical. Explain visible product consequences, correctness drift, trust issues, fairness issues, or hard-to-detect corruption only where it clarifies the design.
- Avoid comedy, exaggerated drama, chaotic phrasing, and off-topic commentary.

Transformation Rules:
- Convert dense paragraphs, tables, bullet lists, and visual explanations into smooth spoken prose.
- Explain transitions between ideas explicitly enough that the chapter is understandable without seeing the page.
- Keep important examples, numbers, constraints, and assumptions.
- Remove formatting that is useful only visually.
- Do not invent new requirements, APIs, limits, benchmarks, or system behavior.
- If the source is fiction, memoir, or narrative prose, preserve scene flow and emotional continuity instead of forcing a technical outline.

Structure And Navigation:
- For technical or explanatory chapters, include concise markdown topic headings by default.
- Prefer headings formatted as `## Heading Title`.
- Preserve meaningful source subchapter headings as markdown headings when they exist.
- You may simplify a heading, but keep the same conceptual boundary.
- Do not flatten all headings into ordinary paragraphs.
- Do not use decorative headings.
- Good heading patterns include core challenge, requirements, scale, data model, API design, write path, read path, correctness, recovery, observability, scaling limits, and final recommendation.
- For fiction or narrative prose, use minimal headings only when the source already has chapter or scene headings.

TTS Constraints:
- Do not use stage directions such as `[Pause]`, `[Short pause]`, or `[Emphasis]`.
- Do not use standalone pause markers on separate lines.
- Do not rely on ellipses as the main pacing tool.
- Use natural punctuation, shorter sentences, rhetorical questions, and paragraph breaks for cadence.
- Do not use markdown tables, bullet lists, or fenced code blocks in the final script.
- Use markdown headings only for section or subchapter titles.

Output:
- Output only the final narration script.
- Do not explain your process.
- Do not add metadata, summaries, or commentary outside the script.
